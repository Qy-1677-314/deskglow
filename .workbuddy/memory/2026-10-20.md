## 修复：Dock 在 Win+D/显示桌面后消失 + 打开应用时不应置顶挡窗口

用户诉求（两层 Z 序需求合一）：
1. Win+D 或点击任务栏右下角「显示桌面」后，Dock 不应消失（应留在桌面层可见）。
2. 打开其它应用时 Dock 不应置顶阻挡窗口（应压在普通窗口之下、桌面之上）。

### 用户实测反馈（第二轮）
- ✅ 第 2 条已正常：Dock 被压在普通窗口下面、不挡窗口，缩小窗口后可见。
- ❌ 第 1 条仍失败：Win+D 后 Dock 在桌面底部不可见。

### 决定性诊断（用截图 + Win32 API 探测实测）
- 环境：Win11 24H2，build 10.0.26200.0。
- 探测 Win+D 后 Dock 窗口状态：`vis=True iconic=False cloak=0 iswin=True`，rect 完全不变 —— **窗口 Win32 状态一切正常，没有被最小化/移出屏幕/cloak**。
- 截图像素对比：Win+D 前 avg=729，Win+D 后 avg=379（明显变暗），恢复后 avg=732 —— **Dock 的渲染内容确实消失了**，露出下面的壁纸。

### 真正的根因（与 v1.3.1 记录的「setVisibleOnAllWorkspaces」不同）
- Electron 33（Chromium 130+）里 `--disable-backgrounding-occluded-windows` 开关**已废弃失效**。
- Windows「显示桌面」触发 Chromium 的**原生窗口遮挡检测（Native Window Occlusion）**，判定 Dock 被遮挡 → 停止 GPU 合成 → 透明 Dock 一帧不画（窗口 Win32 状态完全正常）。
- `backgroundThrottling:false` 只保证 visibilityState 保持 visible、rAF 继续跑，但**管不到原生遮挡检测**这一套独立机制。

### 最终修复方案
1. **渲染进程 rAF 心跳对抗遮挡**（`src/renderer/dock.js`）：加 `occlusionHeartbeat()`，每帧交替写 `document.documentElement.style.opacity` 在 `1` 与 `0.999999` 之间，肉眼不可见但强制合成器持续提交帧。因 `backgroundThrottling:false`，遮挡时 rAF 仍跑。
2. **补充 Chromium feature 开关**（`src/main/main.js`）：`disable-features` 里新增 `NativeWindowOcclusion,WindowsNativeOcclusionTracker`。
3. **运行时双保险**（`src/main/main.js`）：`ready-to-show` 里显式 `dockWin.webContents.setBackgroundThrottling(false)`。

### 走过的弯路（已回退）
- 曾尝试「SetParent 把 Dock 挂到 WorkerW/Progman 桌面窗口」方案（Rainmeter 思路）。实测：本机 Progman 直接含 SHELLDLL_DefView（Win11 标准结构），但跨进程 SetParent 到 Progman 后 `GetParent` 仍返回 0 —— **SetParent 未生效**（疑似 UIPI 或 Electron owner 窗口机制），已回退到原始层级方案。

### 最终代码状态

- `main.js` 的 `reviveDock`/`onMode`/`sinkDock` 恢复原始逻辑，仅保留我上一轮加的 `reviveDock` 结尾 `sinkDock()` 注释与 `setInterval` 的 `needFull` 增强。

## 更新（下午）：搜索 Nexus 后，更正根因 + 找到确定性方案

### 更正：rAF 心跳方案实际无效（已被用户「仍然消失」证实）
- 之前归因于「Chromium 原生遮挡检测误判」是错的。Win+D 是**真遮挡**：系统把隐藏的 `WorkerW` 窗口显示出来并升到最顶层，同时把 `SHELLDLL_DefView` 的父窗口从 Progman 改成 WorkerW（cnblogs 实证）。
- 这是一个真实存在的遮挡窗口，Chromium 的 Native Window Occlusion 正确判定 Dock 被遮 → 停止合成。所以 rAF 心跳（只强制页面层持续出帧）**管不到合成层被停**，必然无效。
- 这正好解释了诊断里「rAF 还在跑、capturePage 还能截到内容、但屏幕只剩壁纸」的现象：渲染层没死，是 DWM 没把窗口合成上屏。

### Nexus（Winstep）官方解法机制（开发者原话，2016）
- Win+D 时 Windows **无通知地**把桌面窗口升到最顶层，没有 API 可以覆盖。
- Nexus 做法是**每秒轮询**检测 Win+D 是否生效；检测到后，**临时把 Dock 设为桌面窗口的子窗口（SetParent 到 Progman）**，让 Dock 随桌面一起被升起而可见；Win+D 解除后再还原（否则会永远垫底=Always on Bottom）。代价是会有轻微闪烁（开发者自承是 kludge）。

### 检测 Win+D 的两种方法（比 Nexus 每秒轮询更好）
1. **事件钩子（推荐）**：`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`。当前台窗口类名变成 `WorkerW` 或 `Progman` → Win+D 生效；变回普通窗口 → 解除。即时、无轮询延迟。
2. **轮询 `GetForegroundWindow()` + `GetClassName()`**：判断是否 `WorkerW`/`Progman`（NX 的做法，有 ~1s 延迟和误判）。

### 关键：透明 Electron 窗口（WS_EX_LAYERED）的坑
- Nexus 把自己临时挂成桌面子窗口——它对不透明窗口有效。但 DeskGlow Dock 是 `transparent:true`（WS_EX_LAYERED 分层窗口）。
- 多源确认：跨进程 `SetParent` 把**分层（layered）子窗口**挂到桌面**不可靠**，可能在 24H2 下不渲染或留残影（StackOverflow #69792059、buaq.net「桌面壁纸层 HUD 踩坑实录」）。

### 确定的候选方案（明确支持透明 Electron 窗口）
- **`electron-disable-minimize`**（原生 C++ addon，GitHub 多个 fork）：核心代码就是把 Dock 的 **GWLP_HWNDPARENT（窗口所有者，索引 -8）设为 `SHELLDLL_DefView`（Progman 的子窗口）**：
  `SetWindowLongPtr(hwnd, -8, (LONG_PTR)SHELLDLL_DefView)`。
  - 效果：Dock 成为桌面组件**所有者**（owner）而非子窗口，Win+D 时随桌面一起显示，且**不会被最小化**；README 明确以 `transparent:true` 窗口使用 → 对透明 Electron 有效。
  - owner 关系 ≠ parent 关系：拥有者窗口（非 WS_EX_TOPMOST）仍在普通 Z 序带内、位于其 owner 之上、位于前台应用之下 → **同时满足第 1 条（Win+D 可见）和第 2 条（不挡普通窗口）**。
- **`electron-as-wallpaper`** 的 `attach()` 是 SetParent 到 WorkerW（壁纸/图标之后），适合做壁纸，**不适合做 dock**（会被图标压住、且是真实 child 有分层渲染风险）。

### 下一步（待实施）
1. 用 `electron-disable-minimize` 的**所有者**方案替代 rAF 心跳 + 已失效的 feature 开关（清理 v1 思路的 hack）。
2. 实现方式二选一：① 编译该原生 addon；② 直接在 main 进程用现成的 PowerShell P/Invoke 一次性设 `GWLP_HWNDPARENT=-8 → SHELLDLL_DefView`（本机已验证 -File 方式可 Add-Type），窗口若被 recreate 则重新设置。
3. **必须本机实测**：Win+D 可见性 + 打开普通窗口是否被 dock 压住（owner 方案若意外导致 dock 永远置顶，则退回 Nexus 式「仅 Win+D 期间临时设 owner」的混合方案）。
4. 删除 `tools/` 下临时诊断脚本与截图（diag.ps1/zprobe.ps1/trace.ps1/lab/* 等）。

## ✅ 再次转折（最终生效方案）：根因是「置顶 + 透明」被 Win+D 桌面层盖住

### 关键实验结论（隔离测试 tools/t2，已清理）
- 复刻窗：透明 Electron 窗体（与 Dock 同标志），magenta 实心填充，截图统计 magenta 像素。
- **非置顶（alwaysOnTop:false）透明窗**：Win+D 前后 `mag=29577` 始终可见 → **透明窗体本身不会在 Win+D 下消失**。
- 对照：真实 Dock 在桌面模式被 `onMode` 与 `zorder.Sink` 双重强制 `setAlwaysOnTop(true)`。
- 结论：Win+D 升起的是 DWM 级桌面覆盖层，**置顶的透明窗体被它盖住而消失**；非置顶透明窗体随桌面保留。owner 方案（仅设 GWLP_HWNDPARENT）之所以"依旧不行"，正是因为 Dock 仍是 TOPMOST，覆盖层照样盖它。
- 实验坑记录：.ps1 缺 UTF-8 BOM 会被 PS 以 GBK 解码，中文路径字面量变乱码 → 一律用 `$root`（系统提供，正确）拼接 ASCII 相对路径；BITMAPINFOHEADER 的 `biPlanes/biBitCount` 必须是 `short` 否则结构体 44≠40 字节导致 GetDIBits 返回 0；跨进程 SetParent 到 SHELLDLL_DefView 本机不可靠（parent 仍为 0），但 SetWindowLongPtr(-8) 设 owner 在 lab2 不透明窗上验证过可用。

### 最终代码改动（替代上一轮的纯 owner 方案）
- `src/main/ps/zorder.ps1` `Sink()` 桌面分支：`HWND_TOPMOST` → `HWND_NOTOPMOST`（桌面态不再强制置顶，保持在普通 Z 带、位于桌面之上）。
- `src/main/main.js` `onMode` DESKTOP 分支：**删除** `dockWin.setAlwaysOnTop(true, 'floating')`（保留 showInactive + sinkDock）。
- 保留 `PinToDesktop`（owner=DefView）在 `Sink` 中作为双保险（透明窗 unproven，但无害）。
- 验证：`node --check` main.js/zorder.js 通过；Dock 不再出现 `setAlwaysOnTop(true)`。

### 追加修复：栏阴影被窗口边界裁掉（用户截图确认就是这个影子）
- 现象：Dock 下方 10px 处出现一条**硬边黑色横带**（用户箭头所指）。原因：透明窗高度只比玻璃条多 10px 左右，`box-shadow`（y=14 blur=24）被窗口边界直接裁断。
- 实测数据（截图 + 枚举窗口）：Dock 窗口 rect 207,1315 2148x225（dev px，屏 2560x1600，125%），窗口下沿≈1540，阴影带在 1505~1538 处骤然消失。
- 修复：
  - `dock.css`：新增 `--shpad`（默认 10px），`.stage` 底部 padding 改 `calc(var(--shpad) + 10px)`；收起态 `translateY(calc(100% + var(--shpad) - 11px))` 保持把手在窗口下沿。
  - `dock.js`：新增 `barShadowPad(a)` = `blur + max(0,y) + 6`，上下限 10~34（上限是为了别让透明留白变成点不到的桌面；autoHide 时固定 10，免得把热区/把手推到任务栏后面）；`--shpad` 进 `applyAppearance`；`measure()` 里窗高改 `barH + grow + shpad + 10` 并把 `shpad` 一起上报；`layoutKey()` 加入 barShadow/glassOn 触发重新量高。
  - `main.js`：`dock:measure` 记住 `shpad` 写进 `lastDockSize`；`dockTarget()` 的 y 改成 `wa.bottom - h + shpad - offset`，这样窗口只向下长、玻璃条在屏幕上的落点不变。
  - `dock.js` document 级 contextmenu：只有落点靠近 `.bar` 才弹 Dock 菜单（否则下方阴影留白会顶掉桌面右键）。
- 计算校验：窗口顶边 = `wa.bottom - barH - grow - 10 - offset`，与 shpad 无关 → 条不动、窗口向下扩展 shpad。
- 待用户重启实测：Dock 下沿的阴影应是柔和渐隐，不再有硬边黑带；面板「外观→描边与阴影→栏阴影」的模糊/下移可实时生效（此前被 10px 裁切，滑杆几乎看不出效果）。
