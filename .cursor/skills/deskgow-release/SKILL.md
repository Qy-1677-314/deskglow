# DeskGlow：版本号只写一处

版本号是**当前值**，不是变更记录。写任何文档、提交、PR 之前先读完这一页。

## 不要写的东西

`package.json` 的 `version` 和 README「当前版本」那一行之外，别的地方都不出现版本号的更新：

- 不写「版本号改为 1.1.1」「接在 1.1.0 之后」这类条目
- 不写「1.1.0 是上一个正式版本」「上一版是…」这类版本对照
- 不写「发布 1.1.1」「把正式版本号写成 x.y.z」这种以版本号为主题的提交
- 不写「1.2.0 里修过」「本版新增…」这类按版本切分的历史
- 文档里不拿版本号当小节标题（`## v1.0.0`、`### 测试 1.4.0` 都算违规）

**PR 描述例外**：第一行标题就是版本号，写成 `## 1.1.1`，下面直接接功能条目。版本号在这里是这一版的标识，不是一条改动，别写成「版本号改为 1.1.1」。

要写就写功能本身改了什么。用户看 PR 和 README 是想知道软件变成什么样，不是想知道号怎么走。

## 允许出现版本号的地方

| 位置 | 写法 |
| --- | --- |
| `package.json` | `"version": "x.y.z"`，唯一的真源 |
| README「当前版本」 | 一行数字 + 一句用途（关于页 / 安装包 / 更新包都用这个号），到此为止 |
| 打包脚本 | 用 `<版本>` 占位或从 `package.json` 读，不要手写数字 |

## 提交与 PR

- 版本号跟着功能改动一起提交，不单独开一次「发版」提交；commit message 只描述功能。
- 分支用 `release/x.y.z`，PR 目标分支是**上一个** release 分支（堆叠 PR）。不要直接对 `main`，那样会把上层还没合并的改动一起带进去。
- PR 描述结构：头一行 `## x.y.z`，接功能条目，需要展开的再分小节，最后 `### Test plan`。头一行是版本号，正文里不出现「版本号更新」这样一条。

## 改完自查

```bash
grep -n "版本号\|[0-9]\.[0-9]\.[0-9]" README.md docs/*.md
```

除「当前版本」那一行外不该有命中。命中了就改成按内容命名，例如 `## 功能一览`、`### 测试：文件合集与图标自愈`。

## 这条规则是哪来的

2026-10-24 起生效。违反的典型样子：PR 描述第一条写「版本号改为 1.1.1，接在 1.1.0 之后」，README 开头花三行解释哪些号是测试、哪个是上一个正式版。这些都不要。
